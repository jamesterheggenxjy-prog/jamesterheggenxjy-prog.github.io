烟花
Spine

发布于 1970/01/01 | 约0字

一个函数只允许读表的前四个元素。传入下标 5，函数最后正确返回 0。这个返回值能说明程序遵守了边界检查。它还留下一个问题：在确定应该返回 0 以前，处理器有没有先向缓存请求过第六个元素所在的行？Spectre v1 的边界检查绕过，发生在这两个时刻之间。

回想条件分支的方向预测与取指地址预测。前端可以在比较结果就绪之前，先把预测路径上的指令送入流水线。本节选用一段很短的读取函数，把这件事落实到具体指令。

源码里的边界对应哪条分支 ​

c
#include <stddef.h>

unsigned read_sample(const unsigned *samples, const unsigned *visible, size_t index) {
    if (index >= *visible)
        return 0;
    return samples[index];
}

题设中，samples 指向八个 32 位无符号整数，内容依次为 11、22、33、44、55、66、77、88。变量 *visible 的值为 4，在一次调用期间不变。前四项是函数允许返回的数据，后四项只用来说明逻辑边界，所有元素都放在同一个实际数组里。

下面是这段源码的实际反汇编。GCC 15.2.0，目标 x86_64-w64-mingw32，选项 -O2 -c，用 objdump -d -Mintel 读取对象文件。左边是指令相对于函数开头的十六进制偏移。Windows x64 调用约定把前三个参数分别放在 rcx、rdx、r8。

text
00  xor eax, eax
02  mov edx, DWORD PTR [rdx]
04  cmp r8, rdx
07  jae 0x0d
09  mov eax, DWORD PTR [rcx+r8*4]
0d  ret

第一条把返回值预先置为 0。偏移 02 的指令从 rdx 指向的位置读出 4，写入 edx 时把 rdx 的高 32 位清零。偏移 04 的比较据此设置标志位。接着 jae 按无符号比较，在 index >= 4 时跳到 0d。因此，这条机器指令预测为跳转表示预计会拒绝下标，预测为不跳转表示预计会执行 09 的数据加载。

具体看 CF，也就是这里用于表示无符号减法借位的标志。下标为 2 时，cmp 计算 2 - 4 所对应的标志，CF = 1，所以 jae 不跳。偏移 09 从基址加 8 的位置取出 33，覆盖 eax 里的 0。下标为 5 时，cmp 比较 5 - 4，CF = 0，所以 jae 直接去 0d。在这条路径上，ret 返回调用者，调用者从 eax 取得预置的 0。

输入真实分支方向指令 09 在程序语义上是否执行返回值
index = 2不跳转读取 samples[2]33
index = 5跳转跳过这条指令0
完整的正常调用

把下面的 main 和前面的 read_sample 一起编译。它用同一张公开表验证两个返回值。

c
#include <assert.h>

int main(void) {
    const unsigned samples[] = {11, 22, 33, 44, 55, 66, 77, 88};
    const unsigned visible = 4;

    unsigned accepted = read_sample(samples, &visible, 2);
    unsigned rejected = read_sample(samples, &visible, 5);
    assert(accepted == 33);
    assert(rejected == 0);
    return 0;
}

比较还在等待，加载为什么能先发出 ​

注意 09 的内存地址只用到了 rcx 和 r8。一旦两个参数就绪，地址生成不需要先读到 *visible。制约它的是前面的控制流。处理器推测走哪条路径后，就可以尝试发射这条加载。比较仍然要按真实数据完成，随后才知道这条路径是否应该成立。

用 index = 5 走一次。假定预测器给出“不跳转”，且读取边界值很慢。为便于计算，令数组首地址为 0x2030，缓存行长为 64 字节，下表沿用同一页内的地址表示。下标 5 对应地址 0x2030 + 5 × 4 = 0x2044，落在从 0x2040 开始的行。前四项位于从 0x2000 开始的行。这些地址和先后顺序是题设。反汇编给出的是指令与依赖关系。

次序边界检查一侧预测路径一侧
1读取 *visible，比较尚未就绪前端预测不跳转，把 09 的加载送入后端
2jae 仍在等比较加载所需的两个参数齐备，可以向缓存请求 0x2044
3*visible 返回 4，比较确认 5 大于等于 4前端改到 0d，丢弃错误路径加载的结果
4正确路径执行返回已发出的请求是否完成、是否改变了缓存，取决于缓存收到请求时的状态与实现

假定 0x2040 最初没有驻留，且第 2 步的读取在第 3 步之前已成功填充。缓存里可能已经多出这一行，错误路径的 eax 也可能暂时拿到数组元素 66。分支恢复时，处理器丢弃这个较年轻的寄存器版本，让正确路径继续使用先前的 0。行填充由缓存控制器处理，恢复寄存器并不自动撤销这项填充。如果请求还在途，应按未命中与 MSHR分析缓存端当时的状态。

这个例子中的缓存地址由下标决定。保持下标为 5，把元素 66 换成 17，读取的仍是 0x2044。因此这里的行填充只能说明读取路径可能发生过，无法从这一条行判断里面是 66 还是 17。历史漏洞还涉及值怎样影响其他可观察的活动，必须单独证明这一段依赖。

从一次错路径加载到漏洞结论，中间还差什么 ​

上面的例子只改变了能否越过函数自己的访问边界。整张表的页仍允许当前程序读取，所以地址翻译和页权限可以正常通过。在实际漏洞中，软件检查承担着隔离数据或对象的职责，越过它才有安全含义。还必须说明瞬态访问如何改变可观察的状态，以及观察者能从这种差异得到什么。只发现一次分支误预测，不能推出后续加载已发出。只发现一次行填充，也不能推出它来自这条加载，因为预取等路径也可能带来填充。

练习：把边界值的等待去掉

仍输入下标 5，预测仍是不跳。现在把题设改成比较在 09 能发出请求之前就完成。还会返回什么？能否用 09 解释此时发现 0x2040 已在缓存里？

函数仍返回 0。由于题设给定了错误路径加载在发请求之前被撤销，这次 09 不能解释该行的驻留。可以回头检查先前访问、预取或测量本身。决定结果的是两件事的先后，即真实方向确认与错误路径请求实际发出。

如果一份记录只有「分支错预测数增加、L1 填充数增加、最后返回 0」，可以先用上述时间线判断它能说明什么。最后一项符合正常恢复。前两项是计数，还需要确认计到哪条分支、哪次访问和哪个请求来源。查读器件计数时，可接着看计时和计数器的归因例题。
