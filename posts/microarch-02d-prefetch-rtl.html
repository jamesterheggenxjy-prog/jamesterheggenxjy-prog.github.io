看清观察线和请求线 ​

BAR-fetchers 支持多种接法。本文只取接在 Rocket 核心侧与非阻塞 L1 数据缓存之间的 HellaCachePrefetchWrapperModule。这个包装器直接转接核心和缓存的大部分信号，同时分出观察线，把核心的访问送给步长器。步长器沿另一条线交回候选，经一项队列进入缓存原有的请求端口。

接口或部件接收什么留下什么或交给谁
核心侧请求入口 io.cpu.req请求地址、命令和其他普通访存字段核心有有效请求时优先使用数据缓存入口
旁路观察 snoop通过包装器筛选的地址与读写标志向步长器给出一次 valid 事件
步长器输出 request步长器内部算出的候选输出地址与读写标志，由暂存队列的 ready 决定该拍是否接收
一项队列 req握手成功的候选保管地址与读写标志，跨过缓存入口仲裁和 s2 校验
包装器的 in_flight预取在缓存入口发生的握手、对应的 s2 事件标记是否已有一次尝试尚待检查
数据缓存 cache.io.cpu对齐后的地址、预取命令和请求属性走缓存的地址翻译与访存路径，回报物理地址和 s2_nack

有两份同名的 req。io.cpu.req 指核心提出的需求请求，源码里的局部变量 req 则是预取暂存队列的出队端。下文把后者简称为队列。最容易读错的信号是队列的 req.ready。它控制何时释放已占用的队列槽，与缓存入口的 ready 属于两个接口。

观察线固定延迟两拍。包装器把核心入口的 fire、当拍命令与地址对齐到 s2。已经接受的核心请求，如果本身是预取命令，或者途中被 s1_kill 取消、在 s2 收到 nack，就不向步长器送出有效观察。snoop 是 Valid 接口，观察方没有 ready 可以要求核心等一拍。缓存命中和未命中的结果也没有作为字段送入这条线。

单流步长器怎样提出候选 ​

步长器接收的是观察地址与读写标志。接口里没有指令 PC，交错访问都进入同一份状态。对照按 PC 分流的 gem5 步长表，这里可以直接看出，决定是否能够维护多条流的不只是算法公式，还有观察接口和寄存器组织。

状态在什么时刻参与计算
last_snoop、last_snoop_2保存最近两次观察。新地址分别与两者求差，任一差值匹配当前 delta，历史计数就增加
last_delta、last_delta_pos保存与最近一次观察的差值和方向，供空闲状态更新步长、进入活跃时记下方向
history_cnt有效观察到来时增减，默认阈值为 4，计数饱和到 7。低于阈值时回到空闲状态
prefetch、pref_far_enough、last_write分别保存候选地址、候选是否离最近观察足够远的注册状态和最近观察的读写属性
state、reset_counter在活跃时允许输出。候选已经走在访问流前面时可进入等待，等新观察追上来。等待过久可触发历史清零

设已记录的两个地址是 0x1108 和 0x1188，最近一次在 0x1188，保存的 delta 为 0x80。现在观察到 0x1208。它与最近一次的差是 0x80，与再前一次的差是 0x100，满足其中一项匹配。若旧计数为 3，且没有触发历史清零，这次更新后便是 4。候选地址生成使用最近一次观察与其差值，此时 0x1208 + 0x80 = 0x1288。进入活跃状态并满足注册的距离条件以后，候选才对队列提出 valid。这一过程从给定的寄存器初态推算，下面的逐拍例题以候选已经有效为起点。

这里距离检查涉及注册状态。valid 由活跃状态和 pref_far_enough 共同决定。正常送出时，候选沿 delta 向前推进，并按已经领先多远决定是否进入等待。观察仍可能在此期间更新，request 使用的是 Decoupled 接口。对这个接口来说，取样时刻是 valid && ready 成立的那一拍。不能把前几拍单独看见的地址当作已经接收的队列内容。

三个事件，三个不同的判据 ​

候选入队。 步长器给出 valid，一项队列为空时提供 ready。两者同时为 1 时，队列在时钟边沿保存地址和读写属性。此处 Queue(..., 1) 用默认的 pipe=false 和 flow=false。空槽刚接收的地址要到下一拍才从出队端可见，满槽释放的当拍也不会用另一个候选补进来。

缓存入口接收。 只有核心的 req.valid 为 0，且队列非空、in_flight 为 0 时，包装器才用队首向缓存端口置 valid。缓存入口此时也给 ready，才发生第二次握手。包装器把 0x1288 向下对齐为 64 字节块首址 0x1280。读候选使用 M_PFR，写意图候选使用 M_PFW，请求指定 phys=false，沿缓存的地址翻译路径继续。握手以后，包装器置位 in_flight，地址还留在原槽里。

确认是否释放队列。 缓存入口握手经过两拍到达 s2。包装器依据 s2_paddr 查询有没有合法的下游管理者，以及相应地址的管理者是否具备这里要求的 AcquireT 能力。检查失败就置 s2_kill。槽位释放却取决于另一根线。若缓存送出 s2_nack，这一项留在队列；否则队列出队，无论本次是否被 s2_kill 取消。两种情况下 in_flight 都清零，下一拍才能提出别的尝试。

因此，看到队列出队，只能确认包装器已经处理完这次入口尝试。判断是否发生缺失请求、是否分配 MSHR、何时返回填充，还要继续看缓存的未命中和填充路径。这个包装器也会屏蔽带预取命令的缓存响应，避免把它交给核心当成一次普通加载的结果。

逐拍跟踪一条被拒绝的请求 ​

设预测器起初提出 P（0x1288）。第 5 拍起，它还可以提出 Q（0x1308），直到 Q 入队。包装器初始为空且未在尝试。除第 2 拍外，缓存入口都就绪。表中队列和 in_flight 是当拍开始时的值，写入寄存器的结果到下一拍可见。表里的合法性与 nack 都是为复算接口而给定的缓存侧条件。

拍核心请求有效队列与 in_flight发生的事
0是空，0P 可以入队。缓存入口给核心
1是P，0P 留在原槽。缓存入口仍给核心
2否P，0包装器提出 P，缓存 ready=0，没有握手
3否P，0缓存入口接受 P 的块地址 0x1280，开始第一次尝试
4否P，1第一次尝试走到 s1，队列仍在保管 P
5否P，1s2_nack=1，留下 P，清除 in_flight。Q 遇到满槽
6否P，0P 在缓存入口再次握手
7否P，1第二次尝试走到 s1
8否P，1s2 合法且无 nack，释放槽位。Q 仍不能在同一拍入队
9否空，0Q 终于入队
10否Q，0缓存入口接受 Q 的块地址 0x1300
11否Q，1Q 走到 s1
12否Q，1Q 的地址检查失败，且无 nack。置 s2_kill 并释放槽位

第 2 和第 5 拍都会导致等待，但发生在不同的路径。第 2 拍尚未握手，in_flight 一直是 0。第 5 拍是缓存对第 3 拍已接收的请求作出延迟拒绝，包装器清除 in_flight，凭保留的 P 发起下一次尝试。Q 第 12 拍被取消的条件也不同。无 nack 让它出队，s2_kill 让缓存停止处理这次尝试。

用代码复算暂存槽的变化 ​

以下 Python 模型从候选已经有效开始。slot 保存队列中的示意地址，s2_cycle 有值时对应 in_flight=1。nack_at 和 kill_at 直接给定缓存侧条件。程序用旧槽位计算本拍能否接收新候选，再更新寄存状态，所以释放队首的那一拍不能补进 Q。复制完整代码用 Python 3 运行即可打印各次握手和 s2 结果。

python
def replay(nack_at, kill_at):
    slot = None
    s2_cycle = None
    next_q = 0x1308
    events = []

    for cycle in range(13):
        core_valid = cycle in (0, 1)
        cache_ready = cycle != 2
        candidate = None
        if cycle == 0:
            candidate = 0x1288
        elif cycle >= 5:
            candidate = next_q
        enqueue = slot is None and candidate is not None
        fire = (
            slot is not None and s2_cycle is None
            and not core_valid and cache_ready
        )

        if fire:
            block_address = slot & ~63
            events.append((cycle, "cache-fire", block_address))
            s2_cycle = cycle + 2

        if cycle == s2_cycle:
            s2_cycle = None
            if cycle in nack_at:
                events.append((cycle, "retain", slot))
            else:
                outcome = "kill-and-pop" if cycle in kill_at else "pop"
                events.append((cycle, outcome, slot))
                slot = None

        if enqueue:
            slot = candidate
            events.append((cycle, "enqueue", slot))
            if candidate == next_q:
                next_q = None

    return events


expected = [
    (0, "enqueue", 0x1288),
    (3, "cache-fire", 0x1280),
    (5, "retain", 0x1288),
    (6, "cache-fire", 0x1280),
    (8, "pop", 0x1288),
    (9, "enqueue", 0x1308),
    (10, "cache-fire", 0x1300),
    (12, "kill-and-pop", 0x1308),
]
assert replay(nack_at={5}, kill_at={12}) == expected
for cycle, event, address in expected:
    print(f"{cycle:2}  {event:12}  {address:#06x}")

对照第 3 拍的 cache-fire 与第 5 拍的 retain。前者记录交给缓存的块首址，后者记录留在队列里的原始候选地址。对于读取模拟波形或计数器的人，这两行对应两类事件。用端口接受次数统计，本例 P 被接受两次。用候选入队次数统计，P 只入队一次。至于下级取行和 L1 填充，程序没有给定这些事件，表里也推不出它们的次数。

练习：第一次尝试没有被拒绝

把代码改为 replay(nack_at=set(), kill_at={12})，其余输入保持不变。P 和 Q 会在哪一拍进入缓存？注意 kill_at 指定的是拍号。

P 仍于第 3 拍进入缓存，但第 5 拍就出队。第 6 拍 Q 入队，第 7 拍 Q 进入缓存，第 9 拍到达 s2。如果要保持 Q 的地址检查结果不变，应把 kill_at 改为 {9}。这次变化来自 P 提前释放暂存槽，候选本身没有改变。
