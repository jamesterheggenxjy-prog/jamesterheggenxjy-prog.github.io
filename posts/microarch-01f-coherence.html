上一篇的写回例题中，核 0 把地址 0x1020 的整数从 5 改成 9。新值留在 L1，下一级可以暂时保留 5。现在增加一个核 1，先让两个 L1 都读到 5，再由核 0 写入 9。核 0 什么时候能写？核 1 之后的读应当到哪里找数据？这两个问题把缓存一致性的权限和数据路径连了起来。

以下追踪一条 64 字节的物理行 A，起点为 0x1000，被修改的字在行内偏移 0x20。两核各有私有 L1，片上共享 L2 保存目录信息。先用便于手算的 MESI 模型讲完主例，再对照 gem5 v24.1.0.3 的 Ruby MESI_Two_Level。文中的交接顺序属于例题题设。

  • 谁保存数据，谁知道该找哪个核
  • 有一份副本，未必已经能写
  • 从两个 5 到两个 9
    • 失效请求发出了，还要等什么
    • 下一级仍是 5，第二个核怎样读到 9
  • 用程序复算失效确认前后的值

谁保存数据，谁知道该找哪个核 ​

图 1 是 gem5 Bootcamp 的 Ruby 控制器组织示意。上层的 L1 控制器分别接各核心，中间的片上互连传输请求、数据和确认消息，下层的 L2 与目录控制器为请求选择数据路径。图概括 Ruby 可连接的控制器类型。本例只使用其中两个 L1 和负责行 A 的 L2。选定的 MESI_Two_Level 把片上的共享者和独占持有者信息放在 L2 行表项中。图上的 Directory controller 还承担到主存一侧的接口，请求行 A 时先看负责它的 L2。

一条行会涉及三处状态。L1 的标记、数据和 MESI 状态决定核心是否能本地读写。L2 行表项包含数据和目录元数据，决定共享者可能在哪些 L1，以及当前的独占持有者是谁。另有在途记录保存一次未完成交接所需的请求者、数据和剩余确认等信息。等确认的计数与缓存行的数据分开保存，写权才能与消息的实际到达顺序相符。

要查的字段Ruby 对照本例用它回答什么
本地数据和权限L1 的 DataBlk、CacheState核 0 的 L1 有 5，还要申请写权吗
共享者集合L2 的 Sharers核 0 写前，哪里可能还有只读副本

有一份副本，未必已经能写 ​

MESI 的四个字母表示私有缓存行在事务收尾后的稳定状态。读权限、写权限和下一级是否已经持有最新数据，可以从状态一起判断。

状态本地能做什么其他副本与下一级
I，Invalid不能用本地这行完成读写要向一致性系统取得副本或权限
S，Shared可读，写之前要升级其他 L1 可能也有可读副本
E，Exclusive可读，能在本地写并转成 M本 L1 独占，数据还未被改过
M，Modified可读写本 L1 独占，且负责在需要时提供最新数据

例如核 0 已经有 S 行，写 0x1020 时标记会匹配，偏移也正确，但还缺一致性写权。它已经持有行中的其余字节，可以申请升级而无需重取整行。若处于 I，局部写入通常既要申请写权，也要取得未被该笔存储覆盖的字节。写分配一节给出了同一地址的字节例子。

写入的过程遵循一个基本约束。同一条行可以有多个读者，获得独占写权之后，只保留一个可写的私有副本。其他核之前持有的只读副本必须被撤销，否则后续读取还会从旧数据命中。

从两个 5 到两个 9 ​

题设给定操作次序，各次操作按表中的顺序完成。L2 开始已有 A 的数据，两个 L1 都处于 I。表中只把偏移 0x20 的字写出来，协议处理的仍是完整缓存行。

操作完成时核 0 的 L1核 1 的 L1L2 对 A 保存的值与目录
核 0 读 AE，5I5，核 0 独占
核 1 读 AS，5S，55，两个核可读
核 0 写入 9M，9I数据仍是 5，核 0 独占
核 1 再读 AS，9S，9更新为 9，两个核可读
核 1 写入 12IM，12数据仍是 9，核 1 独占

第一次只有核 0 读，L2 可以授予 E。这样如果核 0 立即写，便可直接转 M。主例的第二步先让核 1 读，核 0 降为 S。此后核 0 的第一次写要经过升级。

失效请求发出了，还要等什么 ​

将第三行拆开。下表里的“剩余确认”表示核 0 尚需得到多少来自其他副本的确认，记法是教学抽象。

事件核 1 的副本核 0 的写入剩余确认
核 0 申请升级，目录找出核 1仍可读 5等待1
核 1 收到失效，清除本地可用状态，回送确认I确认在路上，仍等待1
核 0 收到最后一个确认，完成升级I写出 9，进入 M0

已发出失效消息，意味着核 1 将来会处理它。在消息真正到达核 1 之前，核 1 仍可能从本地读 5。核 0 等到确认，才知道旧副本已经撤销。两者都成立，就能让旧的 5 和新的 9 对应到不同的访问时段。

gem5 Ruby 中，L1 将 S 状态的存储转入 SM，发送 UPGRADE。L2 在 SS 接到该请求后向其他潜在共享者发失效，同时把需要的确认信息告知请求者，过渡到 SS_MB。请求者凑齐所需确认后可以完成写，并用独占 UNBLOCK 让 L2 结束这一轮。这也解释了为什么只读四个稳定状态会漏掉一段等待。真实实现的确认可能经不同消息到达，计数记法也比上表更细。

下一级仍是 5，第二个核怎样读到 9 ​

核 1 已经没有有效副本，再读会发出 GETS，即申请可共享副本。L2 看到行 A 的独占持有者是核 0。在 Ruby MESI_Two_Level 的 MT 状态中，L2 不能把自己的数据直接当成最新值。它将请求转发给核 0，核 0 把 9 所在的完整数据送到请求者，并把最新数据交给 L2，自己的 L1 降为 S。

这次交接在 L2 所需的两个事件可以先后到达。收到所有者的数据，L2 才能把 5 换成 9。收到请求者的 UNBLOCK，它确认请求者已经拿到所需权限。Ruby 用 MT_IIB 表示两件事都在等，用 MT_IB 和 MT_SB 区分只剩哪一件。两件都到齐后回到 SS。片上 L2 更新成 9，主存什么时候也有 9，还要看 L2 的写回策略。

目录中的共享者记录可以是“可能仍持有”的集合。Ruby 允许私有 L1 的某些干净行静默逐出，因此目录里出现一个核，通常表示需要按协议处理它，不能反过来断言它下一次本地访问一定命中。

用程序复算失效确认前后的值 ​

以下 Python 模型只保存行 A 中被观察的一个字。copies 对应两个 L1 的状态和值，l2 保存共享层此时的数据。升级用一个记录保存申请者、新值和等候确认的核。消息由主程序按给定顺序交付，因此可以在“已经失效、确认还未返回”时检查写入是否生效。将代码保存为 mesi_line.py，使用 Python 3.10 或更新版本运行 python mesi_line.py。

python
from dataclasses import dataclass


@dataclass
class Copy:
    state: str = "I"
    value: int | None = None


@dataclass
class Upgrade:
    requestor: int
    value: int
    awaiting: set[int]


class Line:
    def __init__(self):
        self.l2 = 5
        self.copies = [Copy(), Copy()]
        self.upgrade = None

    def read(self, core):
        local = self.copies[core]
        if local.state != "I":
            return local.value
        if self.upgrade is not None:
            raise BlockingIOError("该行正在升级")
        other = self.copies[1 - core]
        if other.state in ("E", "M"):
            self.l2 = other.value
            other.state = "S"
        self.copies[core] = Copy("E" if other.state == "I" else "S", self.l2)
        return self.l2

    def start_store(self, core, value):
        assert self.upgrade is None
        local = self.copies[core]
        assert local.state in ("S", "E", "M")
        peer = 1 - core
        if local.state == "S" and self.copies[peer].state == "S":
            self.upgrade = Upgrade(core, value, {peer})
        else:
            self.copies[core] = Copy("M", value)

    def invalidate(self, core):
        assert self.upgrade is not None and core in self.upgrade.awaiting
        self.copies[core] = Copy()

    def acknowledge(self, core):
        task = self.upgrade
        assert task is not None and self.copies[core].state == "I"
        task.awaiting.remove(core)
        if not task.awaiting:
            self.copies[task.requestor] = Copy("M", task.value)
            self.upgrade = None

    def show(self, event):
        states = [f"{copy.state}/{copy.value}" for copy in self.copies]
        acks = sorted(self.upgrade.awaiting) if self.upgrade else []
        print(event, *states, f"L2={self.l2}", f"ACK={acks}")


if __name__ == "__main__":
    line = Line()
    line.read(0)
    line.show("R0")
    line.read(1)
    line.show("R1")
    line.start_store(0, 9)
    line.show("UPGRADE")
    line.invalidate(1)
    line.show("INV")
    line.acknowledge(1)
    line.show("ACK")
    value = line.read(1)
    line.show(f"R1={value}")

INV 那一行，核 1 已无可读副本，核 0 仍没有写出 9。等确认进入 acknowledge，核 0 才持有 M 和 9。最后一次 read 模拟核 1 的正常取数，也把所有者回填 L2 和两边转 S 合在一次调用里。前面的 Ruby 对照保留了这两次收尾消息的区别。模型只覆盖主例，直接在 I 状态发起写未命中、替换、同时到达的请求和虚拟网络排队都不在它的接口内。

练习｜核 1 从来没读过 5

在新的 Line() 上先调 read(0)，接着直接调 start_store(0, 9)。有没有失效确认要等？核 1 此时来读会得到几？

核 0 先取得 E。它可以直接写并转为 M，upgrade 仍为空。后来核 1 读时，还是要从独占持有者取出 9。本地升级省掉了失效消息，保留了最新数据交接的责任。

同一条行的先后与不同地址的先后 ​

上面的实验已经给定谁先完成读写。如果一个线程先写数据地址，再写另一个地址的就绪标志，另一核看到标志后何时可以依赖数据，还要看 ISA 的内存顺序和程序的同步操作。单独沿每条缓存行的权限交接推导，无法为不同地址的指令建立顺序。至于两个线程只写不同字段、却仍需要交接同一条行的情形，见伪共享。
