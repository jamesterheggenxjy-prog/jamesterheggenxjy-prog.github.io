一次数据加载怎样查询 TLB ​

假设加载指令要读虚拟地址 VA。处理器先拆出页内偏移和虚拟页号。页内偏移在翻译后保持不变；虚拟页号则要与地址空间标识等信息一起查找已有翻译。TLB 项通常至少要让硬件找到对应的物理页号和访问权限；实际字段、标识与页大小支持随架构变化。

沿用地址翻译篇中的地址 VA = 0x404035e8。按 4 KiB 页切分，低 12 位 0x5e8 是页内偏移，剩余高位构成 VPN = 0x40403。TLB 查询的对象不是整个字节地址，而是能覆盖这个虚拟页的翻译项；若命中，物理页号与 0x5e8 拼接后得到物理地址。若命中项覆盖的是大页，标记只需比较对应的高位页号，更多低位直接属于页内偏移。

先用一个教学模型跟踪一次读请求。取指地址通常查询指令 TLB（iTLB）；数据加载地址通常查询数据 TLB（dTLB）。若一级 TLB 未命中，处理器还可能查询更大的二级 TLB（常称 sTLB）；若仍未命中，页表遍历器（Page Table Walker，PTW）才根据页表读取映射。找到映射后，处理器把翻译结果填入一个或多个 TLB，再继续数据访问。TLB 命中时，地址翻译和权限信息可以直接供后续阶段使用，不必重新读取整条页表路径。

这条“L1 TLB → sTLB → 页表遍历”的顺序是理解用的基线，不代表所有实现都严格串行查询。实际处理器可以并行启动部分查找，存在多个按页大小或访问类型划分的 TLB，也可能缓存页表遍历的中间结果。一次 dTLB 未命中因此不等于一次完整页表遍历；sTLB 命中、中间遍历缓存命中和数据缓存命中是不同事件。地址翻译篇用 CVA6 的 TLB 表项图展示过一个开源实现的具体字段；图中的 CVA6 结构不能当作 Intel TLB 的内部图纸。

TLB 也可以按组和路组织。组决定查哪一小组候选项，路是该组能同时保存的翻译数。地址中的一部分位参与选组，剩余的虚拟页号、地址空间标识、页大小等信息参与标记比较。一次查找大致需要完成三件事：按地址选出一组，比较其中有效路的标记，命中后取出物理页号和权限。若没有匹配项，较低层 TLB 或页表遍历器提供翻译；新项填入时，组内替换规则决定腾出哪一路。真实 TLB 的选组函数与替换策略可能不公开，不能从普通缓存的组织方式直接推断。

不同地址空间的翻译在语义上必须区分。实现可以把 ASID/PCID 等上下文标识作为匹配条件，也可以在上下文切换时执行失效操作；具体组合取决于 ISA、操作系统和处理器。标签区分映射，不等于资源彼此隔离：两个上下文即便不可能把对方的翻译当作命中，仍可能让各自的新翻译竞争同一组的有限路数。页表修改后的 TLB 失效、跨核 shootdown 和地址空间标识回收，属于翻译正确性的一部分，详见跨核同步旧翻译。

TLB 的项关联的是页，不是某条缓存行。以 4 KiB 页为例，同一页内的许多加载共同使用同一页翻译。因此，只知道一次 TLB 驱逐，通常只能推断某个页或页组近期被访问，不能直接确定访问了页内哪个变量。若某个算法在同一页的多个位置之间选择，单纯空间计数可能无法区分它们；还需利用访问发生的先后和时间间隔。

用四路模型算出一次 TLB 驱逐 ​

先把题设定死，避免把真实 TLB 的未知映射混进手算。设 L1 dTLB 有 16 组、每组 4 路，替换采用精确 LRU，虚拟页号对 16 取余决定组号：

set = VPN mod 16

攻击者选四个不同虚拟页号 0x100、0x110、0x120、0x130。它们的低四位都为 0，所以都映射到组 0。受害访问再使用 VPN=0x140，同样映射到组 0，但它是另一页。

步骤组 0 中的翻译项结果
攻击者依次访问四页100, 110, 120, 130四路都由攻击者占用，100 最久未用
受害者访问 VPN=140110, 120, 130, 140新翻译挤掉 100
攻击者探测最旧的 VPN=100无受害访问时命中；有受害访问时未命中读数区分两种题设

下面的 C 程序把这个例子模拟成一个 4 路、16 组的 LRU TLB。vpn 是标签，valid 表示路中是否已有有效翻译，age 用逻辑时间排列新旧。程序报告模型中的翻译未命中数，不测量实际处理器：

c
#include <stdbool.h>
#include <stdint.h>
#include <stdio.h>

enum { SETS = 16, WAYS = 4 };

struct entry {
    uint64_t vpn;
    unsigned age;
    bool valid;
};

struct tlb {
    struct entry set[SETS][WAYS];
    unsigned clock;
};

static bool translate(struct tlb *t, uint64_t vpn)
{
    unsigned set = (unsigned)(vpn % SETS);
    int victim = 0;
    ++t->clock;

    for (int way = 0; way < WAYS; ++way) {
        struct entry *e = &t->set[set][way];
        if (e->valid && e->vpn == vpn) {
            e->age = t->clock;
            return true;
        }
        if (!e->valid) {
            victim = way;
            break;
        }
        if (e->age < t->set[set][victim].age)
            victim = way;
    }

    t->set[set][victim] = (struct entry){vpn, t->clock, true};
    return false;
}

static void run_case(bool victim_access)
{
    struct tlb t = {0};
    const uint64_t attacker[WAYS] = {0x100, 0x110, 0x120, 0x130};
    unsigned misses = 0;

    for (int i = 0; i < WAYS; ++i)
        (void)translate(&t, attacker[i]);
    if (victim_access)
        (void)translate(&t, 0x140);
    /* 本题已知 0x100 是最久未用的一项，只探测这一项。 */
    misses += !translate(&t, attacker[0]);

    printf("victim=%s, probe translation misses=%u\n",
           victim_access ? "yes" : "no", misses);
}

int main(void)
{
    run_case(false);
    run_case(true);
    return 0;
}

两代 Intel 处理器的 TLB 结构实测 ​

TLBleed 论文没有把 TLB 只当作一个抽象方框，而是用性能计数器和冲突访问集逐项测量表的容量、组映射与线程共享关系。下表摘出论文对两个平台的结果；“线性”表示组号按虚拟页号的部分低位计算，“XOR-n”表示选组时异或 n 个连续虚拟地址位。表中的数字描述论文测试的具体微架构，不是 x86 架构保证。

论文测试平台TLB组数 × 路数选组函数两个 SMT 线程间的观察结果
Intel SkylakeL1 dTLB16 × 4线性同组访问会竞争
Intel SkylakeL1 iTLB8 × 8线性未观察到相同的跨线程共享
Intel SkylakeL2 sTLB128 × 12XOR-7共享；线程编号会造成组号偏移
Intel Broadwell XeonL1 dTLB16 × 4线性同组访问会竞争
Intel Broadwell XeonL1 iTLB8 × 8线性未观察到相同的跨线程共享
Intel Broadwell XeonL2 sTLB256 × 6XOR-8共享；组号受硬件线程编号影响

对 Skylake L2 sTLB，论文用虚拟地址位 VA[26:12] 的异或函数计算组号，称为 XOR-7。Broadwell Xeon 的 L2 sTLB 则呈现 XOR-8。这里的“共享”指两个硬件线程的请求会在被测表项集合中产生替换竞争，不表示两个线程可以把对方的地址翻译当作自己的有效映射。论文还观察到 Skylake L2 sTLB 的同组关系受硬件线程编号影响：一个线程的组与另一个线程的组相差 64。读者复现时应把线程偏移和虚拟地址哈希一起纳入选组推导。

共享关系也不能只靠“同一颗 CPU”猜。论文的方法是先构造恰好占满一组的地址集合，再让两个 SMT 线程分别访问候选组，使用未命中计数观察哪一对集合会互相驱逐。换到其他型号、核心类型或虚拟机，层级、页大小、哈希函数和共享范围都要重新核实。TLB 侧信道需要满足相应的同核并发和竞争条件；普通进程切换、跨核运行或单纯同机共存本身不足以保证通道成立。

硬件性能计数器可以帮助逆向研究某次 TLB 访问命中了 L1、命中了二级 TLB，还是触发了页表遍历。TLBleed 论文先用 Linux PMU 事件探索容量、组映射和层级；这一步是研究者的测量工具，并不等于无特权攻击者能读取这些计数器。攻击者模型随后改用一组互相依赖的加载来计时：每次加载的地址由上一次加载结果给出，处理器不能把整组加载并行发出，从而让整组访问的 TLB 延迟反映在总时间中。论文在测量窗口两侧使用 LFENCE 约束计时顺序。

研究团队还把不同虚拟页映射到同一物理页，构造不同的虚拟页标记，同时尽量复用同一物理数据，以减少数据缓存差异。建立这样的映射需要相应权限或实验环境；不能把它说成普通无特权攻击者默认拥有的能力。这个控制实验说明了归因原则：如果要证明读数来自 TLB，就要尽量压低数据缓存给出的旁路差异。否则计时变慢可能来自数据加载本身，无法单独归因于地址翻译。即便完成了控制，还要检查核心迁移、调度、预取和页表状态。

二级 TLB 命中和页表遍历怎样分别计数 ​

设我们只测自己程序中的四次需求加载，想判断一级数据 TLB 未命中之后，翻译究竟由谁提供。以 Intel Skylake Server 的核心事件为例，DTLB_LOAD_MISSES.STLB_HIT 记录一级数据 TLB 未命中但二级 TLB 命中的加载。MISS_CAUSES_A_WALK 记录引起遍历的加载，WALK_COMPLETED 记录完成的遍历，完成时可以成功，也可以报告页错误。三项需要按各自的事件边界解释。尤其不能用「完成了几次」直接代替「有几次加载发起遍历」。

假定这四次加载彼此独立，遍历没有合并，且观测区间包含全部开始和完成事件。下表的周期和结果是教学题设。两次成功的遍历可由不同的页表遍历处理单元并行处理。

加载翻译路径二级 TLB 命中引起遍历遍历完成
A一级数据 TLB 命中000
B一级未命中，二级命中100
C两级未命中，遍历占用周期区间 [10,30)011
D两级未命中，遍历占用周期区间 [16,26)011

在题设下，四次加载有三次一级翻译未命中，但只有两次走到遍历器。B 的翻译由现有的二级表项提供。C、D 即使需要遍历，页表项也可能由页表遍历缓存或数据缓存提供，所以这两次完成事件无法告诉我们向 DRAM 发出了几次读取。

同一平台还给出两个以周期为单位的事件。下面省略共同前缀 DTLB_LOAD_MISSES.。

  • WALK_ACTIVE 每周期判断一次是否至少有一个遍历处理单元在忙。C 覆盖整个 [10,30)，D 完全落在其中，因此题设计 20 个周期。
  • WALK_PENDING 每周期按正在处理加载遍历的单元数累加。两单元同时忙的一拍会计两次，因此题设计为 C 的 20 加 D 的 10，共 30。

若先前只读到「两次完成」，还无法判断这两次遍历是重叠还是串行。占用周期提供了另一份证据，但也不能直接当成程序停顿周期。乱序核心可以在等待翻译时执行独立的工作。要解释总耗时，还得核对加载是否在依赖链上，以及计数窗口是否与计时窗口一致。测量窗口的设置见用计时和计数器分析访存。

练习｜保持次数不变，取消遍历重叠

C 仍占用 [10,30)，D 改在 [30,40) 才开始。观测窗口覆盖到第 40 周期，两个周期事件各计多少？

每一拍都只有一个单元在忙，两个事件都计 30。完成次数仍为 2。因此，完成次数相同的两段执行，遍历单元忙碌区间的并集可以不同。

为什么 TLBleed 要观察访问时间，而不只数哪些组被访问 ​

TLB 项对应虚拟页翻译，因此它留下的空间信号比缓存行更粗。两个数组只要落在同一个 4 KiB 页里，读不同元素通常仍使用同一个页翻译；如果两个候选路径访问的页面集合相同，单看“哪些组发生过竞争”就分不出来。TLBleed 的关键观察是：路径虽然访问相同的组，访问这些组的先后时刻仍可能不同。

论文用 libgcrypt 的一段 Edwards 曲线点乘说明这一点。对密钥的每一位，程序都会执行点倍乘；当该位为 1 时，还会执行点加。用不涉及具体库函数的 C 逻辑表示这个控制关系，可以写成：

c
for (int bit = highest_bit; bit >= 0; --bit) {
    point_double(&result, &result);       /* 每一位都会执行 */
    if (secret_bit(secret, bit))          /* 秘密位决定是否执行 */
        point_add(&result, &result, &base);
}

这段代码本身不是 TLBleed 的攻击程序，也没有展示完整密码算法；它只把论文分析的程序路径写成可读代码。点倍乘和点加会访问各自的坐标及临时数据。如果这些数据位于不同虚拟页，或它们对 TLB 组的访问时刻不同，监视线程就可能看到不同的组延迟序列。若两条路径都访问相同的组，简单统计每组总共被驱逐几次仍可能完全相同；区别藏在事件的时间顺序里。

TLBleed 用依赖加载测量目标组延迟，把连续读数按时间窗口组成特征向量。论文以插桩得到的函数边界和真实标签训练分类器：每个样本取函数边界开始的 300 个延迟值，按该样本的均值和标准差归一化，再交给支持向量机区分点倍乘、点加和其他活动。分类结果形成操作序列；因每个密钥位都有点倍乘，额外出现的点加活动可用来推断候选位。实际数据有漏检、误判和周期边界定位问题，所以还需要信号峰值处理和受限的候选搜索来消化错误。论文报告的 EdDSA 恢复结果依赖特定 Intel 处理器、旧版 libgcrypt 实现、同核 SMT 共驻、训练与采样方法；不能据此推断任意算法或任意 CPU 都会泄露。

评估这类观察时，应逐步确认：计时是否能区分已知的 TLB 状态；攻击者地址是否与受害者映射到同一 TLB 组；该 TLB 是否由相关硬件线程共享；命中差异是否来自 TLB 而非数据缓存；受害访问的页和时间是否与待推断状态存在稳定关系。每一步只支持下一步的前提，单次慢访问不等于看到受害者的某条指令，更不等于恢复秘密。

缓存隔离为何没有自动隔离 TLB ​

CAT 限制的是特定缓存层级中新数据可填入哪些路；它不会因此自动把 TLB 的组和路分区。Intel TSX 可以监测特定缓存冲突并中止事务，也不意味着所有 TLB 冲突都会触发同样的中止。地址空间标识能区分不同进程的翻译语义，却不必然消除这些进程对共享 TLB 组的替换竞争。因此，缓存分区、页表隔离和地址空间标签各自保护不同状态，不能互相替代。

地址空间标签怎样与替换竞争同时存在 ​

先看一个明确的教学模型。设一组有四路，表项保存有效位、虚拟页号、地址空间标识和物理页号。查询时，虚拟页号选中该组，只有有效位、页号和地址空间标识都匹配，才能使用表项中的物理页号。这里假设两个地址空间的请求都能使用该组的四路，采用 LRU 替换，并且没有全局映射。实际处理器的组选择、标签和分区方式须按型号确认。

地址空间 A 的标识为 1，B 的标识为 2。初始时该组由 A 的四个翻译填满，按从旧到新排列为 (1, 0x10) → (1, 0x20) → (1, 0x30) → (1, 0x40)。括号内分别是标识和虚拟页号。现在 B 访问页 0x10，题设中它也选中此组。第一项虽然页号相同，标识却不同，因此 B 的查询未命中；B 使用自己的页表取得翻译后，将它填入该组，LRU 换出最旧的 (1, 0x10)。组内此时有 A 的后三项和 B 的 (2, 0x10)。

随后 A 再访问页 0x10，B 的表项不能满足 A 的查询，A 也发生未命中，并需通过下一级 TLB 或页表遍历重新取得自己的翻译。B 无须知道 A 的物理页号，也无法凭自己的标签直接使用 A 的翻译，仍能通过占用同组的一路影响 A 后续的命中情况。一次慢访问包含其他可能原因，测量时还需按前述方法控制数据缓存和调度因素。

把题设改成两个地址空间各自固定使用两路，B 的新翻译只能替换 B 可用的路，那么这个例子中 B 的访问不会直接换掉 A 的表项。若换成两线程共享四路，标签只参与匹配，替换竞争仍然存在。两种结果由表项使用规则决定，不能仅由“有地址空间标识”推出。

TLBleed 论文讨论了关闭 SMT、避免敏感任务与不可信任务共享物理核心，以及由硬件支持 TLB 组或路分区等缓解方向。具体部署需要结合处理器、操作系统调度和工作负载评估。对教材例题而言，最关键的结论是：即使数据缓存不再共享或已经分区，只要其他可观察的微架构表仍共享，其替换活动也要单独纳入安全分析。
